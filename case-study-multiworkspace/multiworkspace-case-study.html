AGENT HANDOFF KIT · 多工作區運用

同一個項目，拆成幾個工作區

已經會用 Agent Handoff Kit？這篇教你把它用在多個工作區，撐起跨對話的長任務
給誰看：你已經裝好 Agent Handoff Kit、會基本的 開工 / 收工，但項目愈做愈大、要拆成幾塊分頭做、而且不是一兩次對話能完成的長任務。這篇不教安裝（那是另一回事），只教怎麼運用。完全沒接觸過的話，先看文末「60 秒入門」。

先講個問題

先講這篇用什麼當例子，你才知道關不關自己的事：你在寫一本書，還要一手包辦它的對外推廣——一邊顧書稿、封面、事實核查，一邊發 Facebook 貼文、預告、上架公告。目標很實在：把書做出來，也把它推出去。（不是寫書也沒關係——凡是同時要顧「核心成品」和「對外宣傳」、又得做上好幾天的項目，道理都一樣，把「書稿／行銷」換成你自己的情境即可。）

這種項目做著做著，就會撞上兩件事。第一，東西多、性質又不同——全堆在同一個資料夾，換個新 AI 對話接手，它分不清哪份是定稿、哪份只是行銷草稿，一改就改錯。第二，任務長——不是一兩次對話做得完的，你今天做一半，明天開個新對話接著做，AI 卻忘了昨天的脈絡。

單一個工作區、靠基本的開工收工，撐得住一條線的長任務；但當項目要同時推進好幾條線（一邊改書稿、一邊跑行銷），全擠在一起就會互相干擾。這篇要解決的，正是這種「複雜、多線、跨多次對話」的長任務該怎麼用 Agent Handoff Kit 來管。

快速對齊 你手上的 Agent Handoff Kit 在做什麼

一句話：它把「交接」變成資料夾裡一份固定文件。

你每次叫 AI 開工、收工，它就自動幫這個資料夾更新一份進度筆記——上次做到哪、下一步、要小心什麼。所以同一個資料夾的長任務，換多少次新對話都接得回。這篇要做的，是把這個能力從「一個資料夾」放大到「幾個資料夾分工」。

先懂概念 真源歸真源，執行歸執行

先釘一個說法：這篇講的「工作區」，就是你電腦上的一個資料夾，每個資料夾各自裝著 Agent Handoff Kit。一個項目用幾個資料夾，就是幾個工作區。

把核心那一塊——成品、事實核查、披露邊界——放主工作區，這裡是真源（唯一正確的正本，以它為準）。對外那一塊——貼文、預告、發布記錄——放一個行銷工作區去執行。兩個資料夾各自留各自的進度筆記，各做各的長任務，不會互相干擾。

例子裡是兩個，但數字不是上限。同一個項目，你大可以按任務再多開幾個（書稿一個、視覺一個、行銷一個、客服一個……），每多開一個，就多寫一份交接包交給它。主工作區始終守著真源，其他工作區各自執行，只有定了案的決定才回流到主工作區。

運用時會用到兩個相近、但不同的詞，先分清楚：

交接檔Agent Handoff Kit 自動幫每個資料夾維護的進度文件（dev/SESSION_HANDOFF.md）。撐的是同一個工作區、跨多次對話的長任務接力——你叫「收工」它就更新。
交接包由你（或主工作區的 AI）親手寫的一段文字，撐的是跨工作區的交接——把一條任務線交給另一個工作區的 AI，講清楚範圍與邊界。它不是檔案。第 3 步給你範例。

怎麼運用 把長任務分頭交出去

起點假設你已經裝好 Agent Handoff Kit。下面每開一個新工作區，就在那個資料夾跑一次 npx --yes @adamchanadam/agent-handoff-kit@latest init 裝好它（安裝細節不在這篇）。重點在後面五步「怎麼用」。

一眼流程
  1. 按任務把項目分成幾個工作區，各自裝好 Kit
  2. 每個工作區用「開工／收工」撐自己那條長任務
  3. 主工作區寫一份「交接包」，把一條線交出去
  4. 接手的工作區照交接包執行
  5. 只把定了案的決定，回流主工作區
  1. 按任務分工作區
    把核心放主工作區、對外放行銷工作區（需要再多開幾個也一樣）。判斷標準很簡單：會被別人讀錯、改錯的東西，要跟真源分開。書稿正本是真源、放主工作區；行銷草稿天天改、放行銷工作區。每個資料夾各跑一次 init 裝好 Kit。
  2. 每個工作區各自撐長任務
    在每個工作區裡，靠 開工 / 收工 做自己那條跨對話的長任務：開工時 AI 先讀交接檔、告訴你做到哪；收工時它把進度寫回去。所以行銷那條線做到一半，明天換個新對話打「開工」就接得回——主工作區那條書稿線同理，兩條互不打架。
  3. 主工作區寫一份「交接包」，把一條線交出去
    當你要把某塊正式交給另一個工作區做，就在主工作區叫 AI 幫你寫一段交接包（或照下面範例改）。講清楚六件事：哪些是真源、對方負責什麼、可讀哪些檔、哪些不准搬走、什麼情況才回報、未經你批准不准對外發。
    交接包範例（可直接複製、改幾個字就能用）我把這個項目分成幾個資料夾，你負責「行銷」這個。 主資料夾是真源：放成品、事實核查、披露邊界，只有那裡的版本算數。 你的工作：寫對外貼文、預告、發布記錄。 你可以讀主資料夾的成品來理解內容，但不要把書稿原文搬過來改。 任何成品先給我看，未經我同意不要對外發布。 有需要更新主資料夾的事，只在它定案之後告訴我，我再回主資料夾更新。
    不是做出版？六件事不變，把「書稿／行銷」換成你自己的項目情境就行。
  4. 接手的工作區照交接包執行
    到行銷工作區開新對話，先打 開工 讓 AI 讀它自己的交接檔，再把上一步那段交接包貼進去當這條線的指示。順序是：先打「開工」讓它讀自己的交接檔，再貼上一步那段交接包當這條線的指示——兩者不衝突，交接檔是它自己的進度、交接包是你給的任務範圍。交接包貼一次即可；之後這條線做到一半斷了，下次「開工」靠它自己的交接檔接回，不用每次重貼。
  5. 只把定案回流主工作區
    行銷工作區做出來的東西，不要直接倒回主工作區。只有真正定了案、確定要進正本的決定，才回報主工作區、由主工作區更新真源。這條紀律就是讓真源永遠乾淨、不被半成品污染的關鍵。
    怎麼回流：回到主工作區開新對話、打「開工」，把定案那一兩句貼給它，叫它更新真源，再「收工」記錄起來。動作就跟交接包反過來一次——只是這次只帶「定案」，不帶半成品。
    回流範例（從執行端講回主工作區）行銷這邊定案了：書名副標最終用「<…>」、封面用 B 版。 請把這兩項更新到主資料夾的正本；其他還在改的行銷草稿不用進來。

這樣運用之後 你會得到什麼

責任清楚，誰掌真相、誰做執行一看就明；上下文乾淨（每個工作區的 AI 手上只有自己那條線的背景），草稿不會混進正式真源；風險可控，改錯、誤發的機會大減；長任務接得住，每條線換多少次對話都從交接檔接回。項目愈大、線愈多，這樣運用愈划算。

說到底就一句：真源歸主工作區，執行歸各個工作區；交接檔撐同一工作區的長任務接力，交接包撐跨工作區的任務交接。
